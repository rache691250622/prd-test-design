# 面向测试人员的用例设计写法

生成 POINT、SCN、TC 和评审时使用本规范。读者按“具备基本测试操作能力，但不了解本功能”考虑：简单用例看测试点或标题即可判断怎么测；完整用例应让读者无需翻 PRD、追踪链接或其他用例就能执行并判定结果。只写“简洁易懂”无法约束输出，必须做下方文档试读。试读检查描述是否清楚，不运行或尝试执行业务测试，也不要求实际环境和账号已就绪。

## 测试点和标题

- 用一句业务话表达“关键条件 + 操作对象及动作 + 核心预期”，语序自然即可，不强制套句式。例如“未选择礼包时点击批量修改渠道，提示先选择礼包”。对象、动作或判断标准缺失时，测试人员仍需猜测。
- 删除“验证、检查、是否符合需求”等无信息前缀，避免“异常场景、边界校验、状态一致性、幂等性验证”等分类词单独充当测试点。用实际动作和现象表达术语，如“重复提交同一订单，只生成一笔订单”。
- 简洁不设机械字数上限。只保留会改变预期的条件；入口细节、数据准备和次要断言放正文。不得删掉“上线前已存在、未再次登录、实际展示后、同一账号不同设备”等决定结果的限定词，否则句子变短但测试对象已变。
- POINT 表达一条独立业务验证意图；TC 标题表达该意图下的具体条件与结果。POINT 可以对应多条 TC，不把每个输入值都提升为 POINT。用户说“测试点”也可能指 TC 标题，两层都要可读，不额外堆一个重复的“测试点”字段。
- 每条 TC 围绕一个可独立判定的行为。同一操作的提示、数据变化和副作用可以一起断言；不同入口、前置状态或预期分支不能靠“及、以及、各种情况”塞进长标题。等价数据可放明确的数据矩阵；影响结果的关键边界仍须可搜索。

## 正文写清后续测试所需信息

- 前置条件只写执行前必须满足的账号/权限、对象状态和时间/版本条件，一条一个短句；无特殊条件时写“无”。入口用一条短路径放在前置或首步，任选一处即可。业务术语确有理解障碍时只补一句必要解释，不写功能背景、测试目的、通用的网络/环境正常声明或完整准备教程。否则执行前提会被说明文字淹没。
- 测试数据给出可直接输入的示例，或明确的准备方法/筛选条件及准备成功的判断标准；写清对象数量、关键字段、初始值、时间与版本。账号使用示例标识及必要的特征、权限和初始状态描述，不填写凭据，不要求真实账号已分配。不得只写“正常账号、异常数据、有效文件、满足条件”。
- 步骤用短句直接写“动作 + 对象/输入”，如“将渠道改为 B，点击保存”；首次交代入口，切换页面时再补位置，不在每步复述页面名、前置条件和整组数据。不写“测试人员需要、然后进行、以便验证”等叙述。一行一个主要测试动作；同一页面中无独立断言的连续点击、选择、填写可以合并，不把每次鼠标点击拆成一步。存在中间检查、分支、等待、同步点或关键顺序时必须分开，否则合并会掩盖失败位置。禁止“同上、参考 TC-XXX、按需求验证”代替执行信息；追踪链接仅用于追溯。
- 同一用例内各字段分工：前置写必需状态，测试数据写具体值及必要的简短准备方法，操作写动作，预期写结果；用同一对象名关联，避免将同一段信息复制到各处。前置已满足的登录/准备动作不再重演，除非它本身就是测试目标。不能为了简洁引用另一条用例来补足本条信息，也不设固定条数或字数强行删减关键条件。
- 结果写成可核对的现象或数值，如“选中的 2 个礼包渠道变为 B，未选中的礼包仍为 A”；禁止仅写“修改成功、显示正确、结果符合预期”。失败时写清哪些状态/数量不变及允许的恢复行为，不能只看报错提示。
- 并发、迁移、时间边界和故障注入等复杂用例，标题只概括关键条件、动作与核心结果；正文必须保留触发顺序、同步点、准备方法和观测方法。不能为了“无需看步骤”省略这些内容，否则无法重复执行。
- 不为设计完整性虚构入口、按钮名、接口、表字段、精确提示文案、权限规则或并发结果。需求缺少验收口径时列为需求待确认；已定义行为按业务条件描述数据、触发方式、需要观察的对象和预期。未提供实际环境、账号或观测工具不影响用例编写与交付，不索取这些运行资源、不尝试执行，也不标记执行阻塞；来源未说明具体工具或技术路径时，不编造接口地址、表名或工具操作。

## 写法对照

以下均是假设需求已经确认对应行为的表达示例，不能直接作为真实项目的需求来源。

| 不合格写法 | 改写示例 | 原写法会导致什么 |
|---|---|---|
| 批量修改渠道校验 | 未选择礼包时点击批量修改渠道，提示先选择礼包 | 不知道要构造什么条件、触发什么动作 |
| 导入数量边界验证 | 一次导入 101 个礼包，整份拒绝且不新增礼包 | 不知道边界值，也无法判定部分导入是否合格 |
| 失败不扣次数 | 还剩 1 次抽奖机会时抽奖请求失败，剩余次数仍为 1 | 未说明是哪种机会及初始状态 |
| 幂等性校验 | 重复提交同一订单，只生成一笔订单 | 技术分类未表达实际操作和判断标准 |
| 历史数据兼容正常 | 升级后查看升级前创建的订单，金额与升级前一致 | 丢失数据形成时间和需要对比的字段 |
| 权限正确 | 只读账号提交渠道修改请求，修改被拒绝且渠道不变 | 无法辨别要测入口可见性还是服务端拒绝 |

前置和步骤也要压缩为执行短句，以下为同一假设用例的写法对照：

| 字段 | 冗长写法 | 简洁写法 |
|---|---|---|
| 前置条件 | 测试人员需要提前使用一个拥有礼包编辑权限的账号完成后台登录，以便能够进行后续的渠道修改操作。 | 已登录后台，账号有礼包编辑权限。 |
| 测试数据 | 为了测试渠道修改功能，需要准备两个目前生效渠道都为 A 的礼包，后续将其中一个改为 B 并检查另一个。 | 礼包甲、乙：渠道均为 A；目标渠道：B。 |
| 操作步骤 | 进入礼包管理页面，找到礼包甲并勾选其复选框，然后找到并点击批量修改渠道按钮；在弹窗中找到渠道选择控件并选择 B，随后点击保存按钮提交修改。 | 1. 在“礼包管理”勾选礼包甲，点击“批量修改渠道”。<br>2. 渠道选 B，点击保存。 |
| 保存后的预期 | 检查操作完成后所选择的礼包渠道是否已经正确更新，同时确认没有选择的礼包不会受到本次修改的影响。 | 甲的渠道为 B，乙仍为 A。 |

## 陌生人试读与评审

逐条检查正式 TC，POINT 同时检查第 1 项；不要只抽查前几条或只查句式关键词：

1. **遮住步骤读标题**：能否说出关键条件、要做的操作、核心结果？简单用例能否据此开始测试？复杂用例能否明确识别测试目标？答不出来就改写，不能靠猜业务补齐。
2. **不打开 PRD 读完整用例**：能否理解业务入口、所需账号特征与数据、操作顺序和可观察结果？用例自身遗漏的业务条件、输入、动作和预期应补齐；正式来源缺少验收口径时列为需求待确认。未提供实际环境地址、真实账号或工具不属于用例设计问题。
3. **反向判失败**：如果出现相反结果，能否指出哪一条具体预期不满足？若只有“正常、正确、一致”，且没有明确对比对象/字段/基准，就不通过。
4. **回看正式来源**：简化后是否漏掉因果边界，或为了让用例完整而补造业务行为？用来源核对条件、结果与副作用；不以易读为由改变需求。
5. **删冗余后复读**：前置是否只剩必需状态？入口、数据和准备动作是否重复？能否删掉解释性套话或合并无独立断言的点击而不影响执行？能删就删；删后仍须通过以上检查，不能以短为由丢掉同步点、时间边界或判断标准。

在既有用例评审文件中记录可读性结论、问题 TC/POINT ID 和改写结果或需求待确认项，不增加交付文件。发现共性问题时检查全部同类用例，包括正常、失败、边界、权限、重复操作、并发和历史数据场景；仅覆盖正式需求适用的类别。

Markdown 的结构校验无法证明陌生人看得懂。必须分别报告结构校验结果与以上语义试读结果，不得用自动校验通过代替可读性评审。

Excel 导出沿用已通过评审的 TC 标题和正文；模板中的“测试点/用例名称/标题”若承担用例标题用途，映射同一业务标题；若字段含义不明则确认后映射，不写成 POINT 编号或模块分类，不机械截断关键条件与预期。保留模板与既有导出确认规则。
